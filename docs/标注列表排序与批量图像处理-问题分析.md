## 一、标注页右侧图片列表：乱序 + 筛选按钮时灵时不灵

### 1.1 结论速览

| 现象 | 真正原因 | 位置 |
|---|---|---|
| 图片列表乱序 | 后端查询**完全没有 `ORDER BY`**，PostgreSQL 返回堆表物理顺序；租约/保存产生的 `UPDATE` 会把行重写到堆尾，所以"多人协作后就乱了" | `app/crud/crud_annotation.py:56` |
| 筛选按钮"有时有用有时没用" | 四个筛选是 **OR（并集）** 逻辑，不是筛选器叠加 | `app/static/js/annotation.js:1478-1508` |
| 搜索框过滤经常错位/失效 | 搜索按 DOM 下标去索引 `this.imageList`，但列表是**虚拟滚动**，DOM 里只有可视窗口的十几项 | `app/static/js/annotation.js:3635-3643` |
| 列表滚动越用越卡 | 每次 `updateImageList()` 都新绑一个 `scroll` 监听，从不解绑 | `app/static/js/annotation.js:1578` |
| 选中高亮偶尔标错行 | `updateImageListSelection()` 同样用 DOM 下标当过滤列表下标 | `app/static/js/annotation.js:4288-4294` |

### 1.2 乱序的根因

图片列表接口：

```python
# app/api/endpoints/annotation.py:278
@router.get("/projects/{project_id}/images")
def get_project_images(project_id, skip=0, limit=50, db=...):
    return image_annotation.get_by_project_id(db, project_id=project_id, skip=skip, limit=limit)
```

它调用的 CRUD：

```python
# app/crud/crud_annotation.py:56
def get_by_project_id(self, db, *, project_id, skip=0, limit=None):
    query = db.query(ImageAnnotation).filter(
        ImageAnnotation.project_id == project_id
    ).offset(skip)          # <-- 没有 order_by
    ...
```

**没有 `ORDER BY` 的 SQL，其返回顺序在标准里是未定义的。** 在 PostgreSQL 上：

1. 刚 `scan` 完的项目，行是顺序插入的，堆顺序 ≈ 插入顺序，看起来"正常"；
2. 一旦发生 `UPDATE`（保存标注、`is_completed` 置位、**尤其是租约的 `locked_by`/`locked_at` 写入**），
   PostgreSQL 的 MVCC 会把该行写成一个新版本、追加到堆尾；
3. 于是「被人认领过 / 被标注过」的图片就跑到列表末尾去了 —— 越用越乱。

所以你的判断是对的：**是多人协作的租约机制把顺序打乱的**，但它只是"触发器"，
根因是这个接口从一开始就没定义过顺序。

> 对照组：`claim_next_image`（`annotation.py:369`）里是有 `.order_by(ImageAnnotationModel.image_name)` 的。
> 也就是说"下一张"的顺序和右侧列表的顺序**本来就不一致**，这也是另一个体感混乱的来源。

补充：`scan_images` 用 `Path.rglob('*')` 收集文件（`annotation_service.py:459`），
`rglob` 的顺序依赖文件系统，也不保证有序 —— 但只要接口加了 `ORDER BY`，这一点就不影响了。

#### 修复（后端，最小改动）

```python
# app/crud/crud_annotation.py
def get_by_project_id(self, db, *, project_id, skip=0, limit=None, order_by="name"):
    query = db.query(ImageAnnotation).filter(ImageAnnotation.project_id == project_id)
    if order_by == "created":
        query = query.order_by(ImageAnnotation.created_at, ImageAnnotation.id)
    elif order_by == "updated":
        query = query.order_by(ImageAnnotation.updated_at.desc(), ImageAnnotation.id)
    else:  # name
        query = query.order_by(ImageAnnotation.image_name, ImageAnnotation.id)
    return query.offset(skip).limit(limit).all() if limit else query.offset(skip).all()
```

> 末尾必须再跟一个 `ImageAnnotation.id` 做 tiebreaker，否则同名（不同子目录）图片之间顺序仍然不稳定。

同时 `get_project_images` 加一个 `order_by: str = "name"` 查询参数透传下去。
`annotation_service.scan_images` 内部那次调用也会跟着变得稳定。

#### 关于"自然排序"（重要）

数据库的 `ORDER BY image_name` 是**字典序**，抽帧产出的文件名会变成：

```
frame_1.jpg, frame_10.jpg, frame_100.jpg, frame_2.jpg, frame_20.jpg ...
```

这大概率不是你想要的。两个方案：

- **方案 A（推荐，零依赖）**：后端只保证一个稳定顺序，前端 `loadImages()` 拿到后用
  `Intl.Collator(undefined, {numeric: true, sensitivity: 'base'})` 做自然排序。
  一行代码，`frame_2 < frame_10` 正确，中文文件名也正确。
- **方案 B**：PostgreSQL 侧安装 `pg_natsort` / 用正则拆数字排序 —— 复杂，且要考虑分页，不建议。

方案 A 的前端片段：

```js
// annotation.js loadImages()
const collator = new Intl.Collator(undefined, { numeric: true, sensitivity: 'base' });
this.imageList.sort((a, b) => collator.compare(a.image_name, b.image_name));
```

如果以后图片量大到要真分页，再回头做方案 B；现在 `limit=10000` 一次全量拉，前端排序完全够用。

### 1.3 筛选按钮"时灵时不灵"的根因

```js
// annotation.js:1478  updateImageList()
const filteredImages = this.imageList.filter(imageData => {
    const hasAnnotations = imageData.annotations && imageData.annotations.length > 0;
    if (!this.showCompleted && !this.showUncompleted && !this.showAnnotated && !this.showUnannotated) return true;
    if (this.showCompleted   &&  imageData.is_completed) return true;
    if (this.showUncompleted && !imageData.is_completed) return true;
    if (this.showAnnotated   &&  hasAnnotations)         return true;
    if (this.showUnannotated && !hasAnnotations)         return true;
    return false;
});
```

四个条件是 **OR（取并集）**。带来的直接后果：

| 你的操作 | 你以为 | 实际 |
|---|---|---|
| 点【已完成】 | 只看已完成 | ✅ 正确 |
| 再点【已标注】 | 已完成 **且** 有标注 | ❌ 已完成 **或** 有标注 —— 列表反而**变长** |
| 【未完成】+【未标注】 | 交集 | ❌ 并集，几乎等于全部 |
| 【已完成】+【未完成】 | —— | 等于全不筛，列表复原 |

而"未完成"和"未标注"这两个集合在实际数据里高度重合（没标注的基本都没完成），
所以**在一个筛选已经开着的时候再点第二个，看上去就"什么都没发生"** —— 这就是"有时有用有时没用"的由来。

#### 修复：拆成两组互斥单选 + 组间 AND

语义上这四个按钮其实是**两个维度**：

- 维度一 · 完成状态：`全部 / 已完成 / 未完成`
- 维度二 · 标注状态：`全部 / 已标注 / 未标注`

```js
// 状态：this.completedFilter = 'all' | 'completed' | 'uncompleted'
//       this.annotatedFilter = 'all' | 'annotated' | 'unannotated'
const filteredImages = this.imageList.filter(img => {
    const hasAnn = !!(img.annotations && img.annotations.length);
    if (this.completedFilter === 'completed'   && !img.is_completed) return false;
    if (this.completedFilter === 'uncompleted' &&  img.is_completed) return false;
    if (this.annotatedFilter === 'annotated'   && !hasAnn) return false;
    if (this.annotatedFilter === 'unannotated' &&  hasAnn) return false;
    return true;
});
```

按钮点击时：同组内点已激活的按钮 = 取消回 `all`，点另一个 = 切换。
这样"已完成 + 未标注"（= 误标成完成的脏数据）这种真正有用的组合才查得出来。

同时建议在列表顶部显示 `显示 N / 共 M 张`，让筛选是否生效一眼可见 ——
现在 `total-images` 永远显示 `this.imageList.length`（全量），筛选后没有任何反馈。

### 1.4 顺带发现的三个 Bug（同一段代码，建议一起修）

**(a) 搜索框在虚拟滚动下完全错位** — `annotation.js:3635`

```js
filterImages() {
    const imageItems = document.querySelectorAll('#image-list .annotation-item'); // 只有可视窗口 ~20 项
    imageItems.forEach((item, index) => {
        const imageName = this.imageList[index].image_name.toLowerCase(); // 用 DOM 下标去索引全量数组
        item.style.display = imageName.includes(searchTerm) ? 'block' : 'none';
    });
}
```

DOM 里只有可视区域的十几个元素，且它们对应的是**过滤后列表**从 `startIndex` 开始的一段，
而这里拿 `index`（0,1,2…）去索引**全量 `imageList`** —— 匹配的名字和显示的行根本不是同一张图。
而且一滚动就会 `renderVisibleItems()` 重建 DOM，`display:none` 全部丢失。

修法：把搜索词并入 `updateImageList()` 的过滤条件里（`this.searchTerm`），走同一条数据流，
`filterImages()` 只负责 `this.searchTerm = value; this.updateImageList();`。

**(b) scroll 监听泄漏** — `annotation.js:1578`

```js
imageListContainer.addEventListener('scroll', renderVisibleItems);
```

`updateImageList()` 每次调用都新建一个 `renderVisibleItems` 闭包并绑定，**从不解绑**。
保存一次标注、切一次筛选就多一个监听器，标注一小时后可能挂着上百个闭包，每次滚动全部触发，
它们各自持有旧的 `filteredImages` 和已被 `innerHTML=''` 摘掉的 DOM 节点 —— 内存泄漏 + 滚动卡顿。

修法：容器只绑一次（在 `init` 里），`renderVisibleItems` 从 `this` 上读最新的 `filteredImageList`。

**(c) 选中高亮索引错位** — `annotation.js:4288`

```js
updateImageListSelection() {
    const imageItems = document.querySelectorAll('#image-list .annotation-item');
    imageItems.forEach((item, index) => {
        const originalIndex = this.filteredImageIndices[index]; // 同样是 DOM 下标当数据下标
        ...
    });
}
```

同 (a) 的问题。修 (a) 时一并给每个 DOM 项写上 `dataset.filteredIndex`，两处都按它取值。

**(d) 次要性能问题** — `annotation.js:1513`

```js
this.filteredImageIndices = filteredImages.map(f => this.imageList.findIndex(img => img.id === f.id));
```

O(n²)。10000 张图 = 一亿次比较，每次切换筛选都跑一遍。改成先建一次 `id -> index` 的 `Map`。

## 二、图像处理：能不能批量？能不能拼图？

### 2.1 结论速览

**后端能力其实已经有了一大半，缺的是前端入口。**

| 能力 | 服务层 | API 端点 | 前端 | 状态 |
|---|---|---|---|---|
| 单图预处理（缩放/降噪/锐化/亮度对比度/翻转/旋转/加噪/透视） | ✅ `opencv_service` | ✅ `POST /opencv/preprocess` | ✅ | 可用 |
| **批量预处理** | ✅ `batch_process_images` (`opencv_service.py:350`) | ✅ `POST /opencv/batch-process` (`opencv.py:100`) | ❌ **无任何调用** | **后端现成，前端缺入口** |
| Mosaic 四宫格拼图 | ✅ `apply_mosaic` | ✅ `POST /opencv/advanced-augmentation` | ⚠️ 需手动选 4 个文件，一次出 1 张 | 可用但难用 |
| CutMix / MixUp / 天气效果 | ✅ | ✅ 同上 | ⚠️ 同上，一次两张 | 同上 |
| **任意 N×M 网格拼图** | ✅ `create_grid_image` (`opencv_service.py:938`) | ❌ **未暴露** | ❌ | **服务层现成，缺 API** |
| 对比拼图（带标题） | ✅ `create_comparison_image` (`opencv_service.py:896`) | ⚠️ 仅 `/opencv/compare-images` | ⚠️ | 部分可用 |
| 数据集级增强（连 YOLO 标签一起变换） | ✅ `augment_dataset` | ✅ `POST /opencv/augment-dataset` + 进度轮询 | ✅ | 可用 |

### 2.2 为什么现在"只能一张一张处理"

前端全部写死取第一个文件：

```js
// opencv-tools.js:173
const imageFile = document.getElementById('image-upload').files[0];   // 单张
// opencv-tools.js:739-742
const image1 = document.getElementById('mosaic-image1').files[0];     // 四个独立 input
const image2 = document.getElementById('mosaic-image2').files[0];
const image3 = document.getElementById('mosaic-image3').files[0];
const image4 = document.getElementById('mosaic-image4').files[0];
```

对应的 HTML 也没有 `multiple`：

```html
<!-- index.html:558 -->
<input class="form-control" type="file" id="image-upload" name="image" accept="image/*">
<!-- index.html:873/877/883/887 -->
<input class="form-control" type="file" id="mosaic-image1" ... required>
```

对比一下抽帧模块，它是**已经支持多选**的（`index.html:1027` 有 `multiple`），
所以项目里已有可直接照抄的交互范式。

而后端 `/opencv/batch-process` 早就写好了、签名是 `images: List[UploadFile]`，
只是**从来没有前端调用过**。这是最容易吃到的红利。

### 2.3 改造方案

#### 方案 1 —— 批量预处理（改动最小，收益最大）

只动前端：

1. `index.html:558` 的 `image-upload` 加 `multiple`；
2. `opencv-tools.js:173` 改成遍历 `files`，`formData.append('images', f)` 逐个塞；
3. 端点从 `/opencv/preprocess` 换成 `/opencv/batch-process`；
4. 结果用返回的 `batch_id` + `/opencv/processed/{batch_id}/{filename}` 渲染成缩略图网格。

**后端一行不用改。**

建议再补两件事（后端小改）：

- `batch-process` 目前是**同步阻塞**的，几百张图会把请求卡死。
  参考同文件里 `augment-dataset` 已有的 `BackgroundTasks` + `augmentation-status/{id}` 轮询模式改成异步；
- 加一个"打包下载 zip"的端点（抽帧模块 `frame_extraction` 已经在产出 zip，可直接复用其写法）。

#### 方案 2 —— 从数据集/标注项目直接批量处理（不用上传）

现在所有 OpenCV 功能都要"上传文件"，但图片其实已经在服务器上了
（`annotation_projects.image_directory` / `datasets/`）。
`opencv-tools.js:28` 已经在拉数据集列表了，说明这个思路本来就在设计里。

建议新增：

```
POST /opencv/batch-process-directory
  { source: "dataset" | "annotation_project", source_id: "...",
    operations: [...], output_mode: "new_dataset" | "in_place" | "download" }
```

这才是"批量"真正该有的形态 —— 几千张图不可能靠浏览器上传。

#### 方案 3 —— 拼图（网格 / Mosaic）

分两种需求，建议都做，但入口分开，别混在一起：

**(a) 数据增强用的 Mosaic**（YOLO 训练里那个 4 合 1）
现状：4 个 input，一次出 1 张，纯手工。
改造：给一个"批量 Mosaic"入口 —— 选一个数据集/目录 + 填"生成 N 张" + 是否随机采样，
后端循环 `random.sample(images, 4)` → `apply_mosaic` → 输出到 `advanced_augmentations/` 并打包。

> ⚠️ **重要提醒**：现在的 `apply_mosaic` **只拼图，不变换标签**。
> 如果拼出来的图要拿去训练，四张原图的 YOLO 标注框必须跟着缩放平移到新画布上，否则得到的是一份错标数据集。
> `opencv_service` 里已有 `transform_labels_flip_*` / `transform_labels_rotate` 这类标签变换函数可以参照，
> 但 mosaic 的标签变换目前**确实是缺的**，需要新写。这是本次要不要做训练级 mosaic 的关键决策点。

**(b) 看图用的拼图 / 联系表（contact sheet）**
`create_grid_image(images, rows, cols, cell_size)` 已经写好了，**只是没有 API**。
补一个端点即可：

```
POST /opencv/create-grid
  images: List[UploadFile]  (或 source_id)
  rows, cols, cell_size, 是否随机选取, 是否叠加文件名
```

用来快速预览一批抽帧结果 / 一批增强效果，成本极低。

## 四、已确认的决策

> 以下四项已拍板，上文的"可选方案"以此为准。

### 决策 1 · 排序 = 文件名自然排序

后端 `ORDER BY image_name, id` 保证稳定；前端 `loadImages()` 再用
`Intl.Collator(undefined, {numeric: true})` 做数字感知排序，使 `frame_2 < frame_10`。
列表顶部加一个下拉框，可切换 `文件名 / 扫描顺序 / 最近修改`，默认「文件名」。

### 决策 2 · 筛选 = 两组单选，组间 AND

```
完成状态：[全部] [已完成] [未完成]      ← 组内单选
标注状态：[全部] [已标注] [未标注]      ← 组内单选
                    ↓ 组间取交集
              显示 128 / 共 2043 张
```

点击组内已激活的按钮 = 取消回「全部」。搜索词并入同一条过滤链，不再操作 DOM。

### 决策 3 · 批量处理 = 上传多选 + 服务器目录，且都异步带进度条，并支持按比例随机抽样

三条入口全做：

1. **多选上传** — 预处理 tab 的 input 加 `multiple`，接已有的 `/opencv/batch-process`；
2. **选服务器上的数据集 / 标注项目** — 新增 `/opencv/batch-process-directory`；
3. **按比例随机抽样** — 不是整个数据集都处理，而是"从里面随机选 20%"。

抽样参数设计：

```
POST /opencv/batch-process-directory
{
  "source": "dataset" | "annotation_project",
  "source_id": "...",
  "split": "train" | "val" | "test" | "all",     // YOLO 目录结构 {train,val,test}/{images,labels}
  "sample": { "mode": "ratio" | "count" | "all", // 随机抽样
              "value": 0.2,                       // ratio 时是比例，count 时是张数
              "seed": 42 },                       // 固定种子，结果可复现 / 可复查
  "operations": [ {"name": "denoise_image", "params": {"strength": 3}}, ... ],
  "output_mode": "new_dataset" | "in_place" | "download"
}
```

要点：

- **`seed` 必须暴露给用户**。随机抽样如果不可复现，出了问题没法复查是哪 20% 被改了；
  结果清单也要落盘（`manifest.json` 记录被选中的文件名列表）。
- **`output_mode` 默认 `new_dataset`，绝不默认 `in_place`。** 就地覆盖原图是不可逆操作，
  且当前 `batch_process_images` 是按 `basename` 写出的（`opencv_service.py:392`），
  就地模式会直接覆盖源文件。若要支持 `in_place`，必须先备份或强制二次确认。
- **标签怎么办**：抽样处理后，被选中的图对应的 `labels/*.txt` 要一起复制到输出目录，
  否则新数据集只有图没有标注。几何类操作（旋转/翻转/透视）还必须调用已有的
  `transform_labels_rotate` / `transform_labels_flip_*` 同步变换标签；
  像素类操作（降噪/亮度/锐化/加噪）标签原样复制即可。
  **建议前端在 UI 上把这两类操作明确分开标注**，避免用户误以为随便选都安全。
- **异步化**：照抄同文件 `augment-dataset` 已有的 `BackgroundTasks` + `/opencv/augmentation-status/{id}` 轮询模式，
  统一成 `/opencv/task-status/{task_id}`，前端复用 `opencv-tools.js:537` 那段轮询代码。
- 完成后提供 zip 打包下载（可复用 `frame_extraction` 里已有的打包写法）。

### 决策 4 · Mosaic = 进训练集，且需要「预览 → 采纳/丢弃/暂留」的人工审核流

这条的工作量最大，因为它同时需要**标签变换**和**审核状态持久化**。

#### 4.1 必须新写 mosaic 的标签变换

⚠️ 现有 `opencv_service.apply_mosaic`（`opencv_service.py:1064`）**只拼像素，不动标注框**。
既然产物要进训练集，就必须新增一个返回 `(图像, 变换后的标签)` 的版本：

```python
def apply_mosaic_with_labels(images, labels_list, out_size) -> (np.ndarray, List[List[float]]):
    # 对每一张子图 i：
    #   1. 记录它被缩放到的目标尺寸 (sw, sh) 和在画布上的偏移 (ox, oy)
    #   2. YOLO 归一化坐标 -> 原图像素坐标 -> 乘缩放比 -> 加偏移 -> 除以画布尺寸重新归一化
    #   3. 裁剪越界部分；若裁剪后框面积 < 原面积的某个阈值（常用 0.2）则丢弃该框
    #   4. class_id 保持不变（前提：四张图来自同一数据集，类别表一致）
```

关键细节：

- **越界框处理**是 mosaic 标签变换最容易写错的地方，必须裁剪 + 按残余面积比过滤，
  否则会产生大量只剩边角的垃圾框，反而拉低模型精度；
- **四张图必须来自同一个数据集/标注项目**，否则 `class_id` 对不上，会静默产出错标数据；
- 项目里已有 `transform_labels_rotate` / `transform_labels_perspective`（`opencv_service.py:505/593`）
  可作为坐标变换的写法参照，但 mosaic 的逻辑需要独立实现。

#### 4.2 审核流：预览 → 采纳 / 丢弃 / 暂留

期望的交互：

```
[生成一张] → 预览（拼图 + 叠加变换后的标注框，便于肉眼校验标签对不对）
              ↓
      [加入训练集]  [丢弃]  [暂留]
              ↓         ↓       ↓
        写入数据集   删文件   留在待定区，稍后再决定
              ↓
        自动生成下一张，继续审核
```

因为有「暂留」这个第三态，**状态必须持久化**，刷新页面 / 换台机器不能丢。建议新增一张表：

```python
class MosaicCandidate(Base):
    __tablename__ = "mosaic_candidates"
    id          = Column(UUID, primary_key=True, default=uuid.uuid4)
    dataset_id  = Column(UUID, ForeignKey("datasets.id"))   # 来源数据集
    source_images = Column(JSON)      # 参与拼图的 4 个源文件名，便于溯源
    image_path  = Column(String)      # 拼图产物路径（待定区）
    labels      = Column(JSON)        # 变换后的 YOLO 标签
    status      = Column(String, default="pending")  # pending / accepted / discarded
    seed        = Column(Integer)     # 该次随机采样的种子，可复现
    created_by  = Column(Integer, ForeignKey("users.id"))
    created_at  = Column(DateTime, default=datetime.utcnow)
```

配套端点：

```
POST   /opencv/mosaic/generate      # 指定数据集 + 张数，随机采样 4 张生成候选（status=pending）
GET    /opencv/mosaic/candidates    # 列出待审核的，支持按 status 过滤
POST   /opencv/mosaic/{id}/accept   # 采纳 -> 写入目标数据集 train/images + train/labels
POST   /opencv/mosaic/{id}/discard  # 丢弃 -> 删文件 + 标记
                                     # 暂留 = 不调用任何接口，保持 pending 即可
```

「采纳」的落盘位置遵循项目现有的 YOLO 布局（`datasets_import/sitting_pose/` 已是此结构）：

```
app/static/datasets/{dataset_id}/train/images/mosaic_{uuid}.jpg
app/static/datasets/{dataset_id}/train/labels/mosaic_{uuid}.txt
```

并同步更新 `datasets` 表的 `image_count` / `train_count`。

> 建议：预览图上**默认把变换后的标注框画出来**（`opencv_service.draw_bounding_boxes` 已有，`opencv_service.py:847`）。
> 人工审核 mosaic 最主要的价值就是肉眼确认标签有没有跟着拼对，纯看图片是审不出问题的。

## 五、还需要你确认的三个小点

1. **Mosaic 采纳后写进哪个数据集？** 是写回源数据集（数据集会越滚越大、且难以回退），
   还是新建一个 `xxx_mosaic` 数据集单独存放（推荐，训练时可选择是否合并）？
2. **暂留区要不要设上限/过期？** 比如最多存 200 张、或 7 天未处理自动清理，
   否则 `pending` 会无限堆积占磁盘。
3. **Mosaic 是一张一张生成，还是先批量生成 20 张再逐张审核？**
   前者交互更简单，后者审核效率高（可以先跳过明显不行的）。我倾向后者：
   一次生成 N 张进待定区，然后在一个网格里逐张点「采纳/丢弃」。

## 六、实施中发现的既有 Bug：旋转增强的标签是错的

> 这不是本次新增代码的问题，而是**已上线的 `augment-dataset`（数据集增强·旋转）本来就存在的缺陷**。
> 因为批量处理要复用同一套标签变换函数，所以必须先说清楚。

### 6.1 复现方式

`rotate_image`（`opencv_service.py:164`）用 `cv2.getRotationMatrix2D(center, angle)` + `warpAffine`，
画布尺寸保持 `(W, H)` 不变；而 `transform_labels_rotate`（`opencv_service.py:505`）对 90°/270°
使用的映射是 `(x,y) -> (1-y, x)` / `(y, 1-x)`。

用 OpenCV 官方的 `getRotationMatrix2D` 矩阵定义做前向仿射映射，逐点核对结果：

| 场景 | 角度 | 代码写入标签 | 图像里目标的真实位置 | 结论 |
|---|---|---|---|---|
| 正方形 480×480 | 90° | x=0.875 y=0.208 | x=0.125 y=0.792 | ❌ 偏差 0.75 |
| 正方形 480×480 | 180° | x=0.792 y=0.875 | x=0.792 y=0.875 | ✅ |
| 正方形 480×480 | 270° | x=0.125 y=0.792 | x=0.875 y=0.208 | ❌ 偏差 0.75 |
| 非正方形 640×480 | 90° | x=0.875 y=0.156 | x=0.219 y=0.938（且被裁） | ❌ 偏差 0.78 |
| 非正方形 640×480 | 270° | x=0.125 y=0.844 | x=0.781 y=0.063（且被裁） | ❌ 偏差 0.78 |

### 6.2 两个独立的缺陷

**缺陷 A · 90° 与 270° 的旋转方向反了（正方形图也中招）**
`cv2.getRotationMatrix2D` 的正角度是**逆时针**，而标签公式 `(x,y) -> (1-y, x)` 是**顺时针**的映射。
两者恰好互为反向 —— 从上表可见，90° 算出来的标签正好等于 270° 的真实位置，反之亦然。
**即 90° 和 270° 的标签被互换了。**

**缺陷 B · 非正方形图片的 90°/270° 还会裁掉画面**
640×480 的图旋转 90° 后内容变成 480 宽 × 640 高，但 `warpAffine` 的输出画布仍是 640×480，
上下被裁掉。而标签公式是按"画布也跟着变成 480×640"推导的，两者前提就不一致。
即使修好方向，非正方形的 90°/270° 依然对不上。

**缺陷 C · 任意角度（非 90 倍数）本就是近似的**
代码注释里已自承"宽高计算比较复杂，这里简化处理"—— 只旋转了框心，宽高原样保留，
且没有处理越界裁剪。不建议在批量处理里开放任意角度旋转。

> 顺带：`flip_image` 的 docstring 写反了（写的是"0: 水平翻转, 1: 垂直翻转"，
> 而 OpenCV 的 `flipCode=0` 是上下翻转、`>0` 是左右翻转）。
> 但**调用方 `augment_dataset` 传的参数和配对的标签变换函数是正确的**，属于纯注释错误，直接改注释即可。
> 翻转、缩放、以及全部像素类操作（降噪/亮度对比度/锐化/加噪）的标签处理都没有问题。

### 6.3 影响面

- 凡是用过「数据集增强 → 旋转」且勾选了 90°/270° 的，产出的数据集**标注框是错的**，
  拿去训练等于喂了一批错标样本；
- 180° 不受影响，翻转、缩放、像素类操作均不受影响。

### 7.3 又修掉一个既有 Bug：中文路径下图像读写静默失败

在 conda 环境 `myolotrain` 里实测（cv2 4.13.0）：

```
imwrite 中文路径 -> False        # 不抛异常，只返回 False
文件是否真的存在 -> False
imread  中文路径 -> None
```

**Windows 上 OpenCV 用 ANSI 编码打开文件**，遇到非 ASCII 路径：

- `cv2.imread` 返回 `None`；
- `cv2.imwrite` 返回 `False` **且不抛异常** —— 这是最危险的，
  而 `save_image` 原本**没有检查返回值**，会一路返回成功。
  批量处理会报告"成功处理 N 张"，但一个文件都没写出来。

项目里 `export_to_dataset` 用 UUID 目录（注释写着"避免中文路径问题"）就是在绕这个坑，
但**导入的数据集目录和标注项目目录仍然可能是中文** —— 你项目里就有 `datasets_import/汽车道路（小）`。
本次新增的批量处理允许直接选标注项目和任意目录，会正面撞上。

#### 修复

在 `opencv_service` 里新增两个 unicode 安全的读写函数，绕开路径编码：

```python
imread_unicode(path)   # np.fromfile + cv2.imdecode
imwrite_unicode(path, image, params)  # cv2.imencode + ndarray.tofile
```

并把所有调用点改过去：

| 位置 | 改动 |
|---|---|
| `opencv_service.read_image` | 走 `imread_unicode` |
| `opencv_service.save_image` | 走 `imwrite_unicode`，**并检查返回值**，失败即抛异常 |
| `opencv_service.extract_frames` (2 处) | 走 `imwrite_unicode` |
| `opencv_service.detect_scenes` / `detect_motion` | 走 `imwrite_unicode` |
| `annotation_service` 自动标注读图 | 走 `imread_unicode` |
| `frame_extraction_service` 抽帧写出 | 走 `imwrite_unicode`（中文视频名会派生中文帧名） |

实测覆盖 `.jpg/.JPG/.jpeg/.JPEG/.png/.PNG/.bmp/.webp/.tif` 及无扩展名，读写均正常。

## 八、追加：拼图进标注任务后标注为空的原因

### 8.1 现象

批量拼图 → 采纳 22 张 → 新建标注任务「拼图」→ 图片都在，但标注全没了。
而人工审核阶段预览图上明明是有框的。

### 8.2 结论：数据没丢

盘上一切正常：

```
app/static/datasets/f73afd4b-.../train/labels/  22 个 .txt，共 123 个标注框
classes.txt / dataset.yaml                      6 个类别，nc: 6
class_id 分布                                    0~5，全部在类别表范围内
```

数据库里的项目「拼图」：

```
类别 6 个 ✓    图片目录正确 ✓    22 张图，0 张有标注
导入原标注: False        ← 原因
```

没勾「导入原标注」时，`scan_images` 只创建空的图片记录（`annotations=[]`），
盘上的 `labels/*.txt` 根本不会被读取。

### 8.3 但这不是操作失误，是功能缺口

`online-annotation.js:1439`（修复前）：

```js
// 当选择服务器目录时，导入原标注功能不可用
if (selectedImageSource === 'directory') {
    importOriginalAnnotationsCheckbox.disabled = true;
    if (isChecked) importOriginalAnnotationsCheckbox.checked = false;  // 强制取消
}
```

拼图数据集的目录是 UUID 命名（`datasets/f73afd4b-.../`），
建标注任务时只能走「服务器目录」，而这个模式下前端**直接禁用并强制取消**了「导入原标注」。

可后端 `_import_existing_annotations_with_stats` 的标签目录查找顺序是：

```python
image_dir_path / "labels"          # .../train/images/labels
image_dir_path.parent / "labels"   # .../train/labels   ← 正好命中
image_dir_path / "Annotations"
```

**能力本来就有，是被前端挡掉的。**

### 8.4 还有一颗地雷：class_id 超范围会被静默丢弃

`_parse_yolo_label_file:267`：

```python
class_id = int(parts[0])
if class_id >= len(classes):
    continue        # 静默 continue，不计数不报错
```

项目类别表比标签里的 class_id 少一个，对应的标注框就凭空消失，界面上没有任何提示。
本次拼图数据集类别是全的（6 个，最大 class_id=5），没踩到；但换个数据集就会踩。

### 8.5 修复

| 位置 | 改动 |
|---|---|
| `online-annotation.js` | 服务器目录模式**不再禁用**「导入原标注」 |
| `annotation_service.import_annotations_from_disk` | 新增。给已存在的项目补导入磁盘标签，**默认不覆盖**已标好的内容 |
| `annotation.py` `/projects/{id}/import-annotations` | 新增端点，`overwrite` 默认 False |

## 九、PT → TFLite 转换的精度损失（实测）

### 9.1 转换链路

`app/api/endpoints/models.py::_export_pt_to_tflite`：

```
PT --ultralytics.export(format=onnx, imgsz=640, opset=12)--> ONNX
    --onnx2tf.convert()--> TFLite（产出 float32 + float16 两个版本）
    --> 代码显式挑 float32 那个
```

关键：**全程没有量化**。`half` 用默认 False，ONNX 权重实测是 `FLOAT32 x182`；
onnx2tf 产出 float32/float16 两版，后端 `float32_files[0]` 明确选 float32。
量化（INT8/FP16）才是精度损失的主要来源，这条链路上没有。

### 9.2 实测结果（用你的 文物mvp-v1_best.pt，YOLO11n，nc=5）

**原始输出张量逐元素对比**（同一张预处理好的图，排除预处理差异）：

| 指标 | 数值 |
|---|---|
| 框坐标通道 最大绝对误差 | **1.13e-03 像素**（640px 画面上 = 1.76e-04 %）|
| 类别分数通道 最大绝对误差 | **2.44e-06**（分数范围 0~1）|
| 全张量 平均绝对误差 | 8.9e-06 |
| 输出量程 | [-26.6, 635.7] |
| 最大绝对误差 / 输出量程 | 1.1e-06 |
| 相关系数 | 1.0000000000 |

**端到端检测对比**（15 张真实图片，两侧用同一套后处理 conf=0.25 / NMS IoU=0.45）：

| 指标 | 数值 |
|---|---|
| 检测框数量与类别完全一致 | **15 / 15 张** |
| 置信度差异 | 最大 5e-7，平均 2e-7 |
| 框坐标差异 | 最大 6e-5 像素，平均 4e-5 像素 |

### 9.3 结论

**这条链路上的精度损失可以忽略。** 误差量级在 1e-6（分数）到 1e-3 像素（坐标），
是 float32 下算子实现差异和 NCHW→NHWC 布局转换带来的浮点舍入，不是精度降级。
置信度差异 5e-7，远小于任何实际会用的阈值步长；框坐标差异 6e-5 像素，肉眼和指标都不可能反映出来。

**真正会让端侧结果不一致的，不是这一步转换，而是下面这些：**

1. **输入尺寸被固定成 640×640**。导出时 `imgsz=640` 写死，模型不再支持动态尺寸。
   端侧必须用和训练时一致的 letterbox 预处理（等比缩放 + 补边 114），
   直接 resize 拉伸会明显掉点 —— 这个影响比转换本身大几个数量级。
2. **导出的模型不含 NMS**。ultralytics 的 ONNX 导出默认 `nms=False`，
   TFLite 输出的是 (1, 4+nc, 8400) 原始张量。端侧要自己实现 conf 阈值 + NMS，
   实现差异（IoU 算法、类内/类间 NMS、最大框数）会直接改变最终检测结果。
3. **归一化方式**。本次测试用的是 /255.0，端侧若用了别的均值方差，结果会完全不同。
4. **端侧如果自己再做一次 INT8 量化**，那才会有实质精度损失，需要用真实数据做校准集并重新评估 mAP。

### 9.4 顺带发现并修复的三个问题

**(1) ONNX 中间文件泄漏到模型目录（已修）**

`_export_pt_to_tflite` 给 `yolo_model.export()` 传了 `project=temp_dir`，
但 **ultralytics 的 ONNX 导出会无视 project/name，把 .onnx 写在 .pt 文件旁边**。
于是每导出一次就在 `app/static/models/` 下泄漏约 10MB，且 temp_dir 的清理扫不到。

你的模型目录里已经有 2 个这样的遗留文件（共约 22MB）：

```
app/static/models/952c38cf-2b56-4b0b-b7e3-93a31025dda2.onnx                     11M
app/static/models/training_0d8c8932-.../exp/weights/best.onnx                   11M
```

修复：先把 .pt 复制进 temp_dir，从副本导出，中间产物就一定落在 temp_dir 里。
实测导出后新增泄漏 **0 个**。
（已有的那两个是你的文件，我没有删，要不要清理你自己决定。）

**(2) verify-tflite 第四步直接崩溃（已修）**

```python
tflite_model = YOLO(tflite_path)
tflite_results = tflite_model.predict(...)   # TypeError
```

ultralytics 8.4.95 的 LiteRT 后端与环境里装的 ai_edge_litert 版本不兼容：

```
TypeError: CreateWrapperFromFile(): incompatible function arguments
```

也就是说**这个验证接口现在是跑不起来的**。已改为直接用 `tf.lite.Interpreter` 推理
+ 自己做 letterbox 预处理和 conf/NMS 后处理，绕开该后端。

**(3) 验证接口只比个数，看不出误差量级（已改进）**

原来只对比"检测到几个目标、哪些类别"，无法回答"精度掉了多少"。
现在返回体里加了 `numeric_diff`：

```json

  "box_max_abs_error_px": 0.001068,
  "class_score_max_abs_error": 1.475e-06,
  "overall_mean_abs_error": 8.93e-06,
  "output_value_range": [0.0, 637.59]

```

实测跑通，且与本节 9.2 的独立测量结果一致。

### 9.5 建议

- 端侧部署前，用 `verify-tflite` 传一张**真实图片**跑一次，看 `numeric_diff`：
  `class_score_max_abs_error` 在 1e-5 以内就说明转换没问题；
- 如果端侧检测结果和 PT 对不上，**先查 letterbox 预处理和 NMS 实现**，不要怀疑转换精度；
- 若为了体积/速度想上 float16 或 INT8，那是另一回事，必须用真实数据重新评 mAP。
  onnx2tf 已经顺带产出了 float16 版本（5.3MB vs float32 的 10.5MB），但**当前代码没有使用它**。
