# 文物视频一键训练：产品可行性评审 + 实施计划（v3）

## Context

目标交付：**一个对外接口 + 一个控制台**，docker compose 部署，只开放一个端口（API 与控制台共用）。
接口：上传一个或多个文物视频（每个视频带类别）→ 自动切帧 → 自动标注 → 自动训练 → 产出 PT + 已校验 TFLite 交付包；出了问题去控制台定位，查看标注数据、类别分布和训练日志。尽量复用现有平台。

已确认的产品决策：
- **复核策略 = 按异常暂停**（取代 v2 的“必经全量复核”）：默认不等人，质量闸门触发才暂停到 `needs_review`；请求里可以传 `review_mode=full` 强制全量复核。
- **自动标注可以用云端 VLM**（OpenRouter / Qwen3-VL）。
- **部署 = compose 单端口**：app + postgres 两个容器，只对外开放一个端口，默认 8000；**端口被占用时自动顺延到 8001、8002……**，并明确告知最终使用的端口。
- **交付物 = PT + 已校验 TFLite 包**。

本文是在 v2（`文物视频一键训练流水线-设计方案.md`）基础上的产品评审与修订版。v2 中未被本文修订的部分（VLM 粗标 → SAM 精修 → 质量闸门、按视频划分、TFLite 三道校验、交付包结构等）继续有效；两者冲突时以本文为准。实施从 M0 开始。

## 一、可行性结论

**可行。现有平台约 60~70% 的底层能力能复用；但现在的状态不能直接对外暴露，安全和部署要先补。**

| 环节 | 现状 | 判断 |
|---|---|---|
| 切帧 | `frame_extraction_service.extract_from_video` 可用 | 直接复用；要改：不再删除源视频（`run_batch` L235-240）、补每帧清单 |
| 清洗 | 有模糊/曝光检测（`opencv_service.py:337/363/389`），没有去重 | 小量新写（视频内分位数 + pHash） |
| 自动标注 | 没有任何 VLM 代码；现有 `auto_annotate_image` 会把有框的图直接标记为完成 | 主体新写 |
| 数据集 | `export_to_dataset` 只写 `train/`，yaml 指向不存在的 `val/`，丢弃无框帧 | 流水线自己按视频划分，不走它 |
| 训练 | 子进程训练可用；4 个阻断 bug（见 H 节） | 复用 + 修 |
| TFLite | `endpoints/models.py:335-524` 能转、能验证，但写死 640、不保存产物、抛 HTTPException | 抽成 service |
| 控制台 | 训练列表、日志弹窗、标注编辑器都有；缺统一任务中心、按类别统计、只读查看、日志增量拉取 | 在现有 SPA 上加页面，不需要重做前端 |
| Docker | GPU 镜像构建会失败（Ubuntu 22.04 默认源没有 python3.12）；会把约 1.7GB 本地数据打进镜像；暴露 5432/6006 | 重写 |
| 安全 | 大部分路由**没有鉴权**；`/static/*` 公开所有数据和模型；目录浏览器能看整个文件系统；CORS 全放开；没有 API Key | **对外前必须修（阻断项）** |

## 二、产品层面的判断与优化点

1. **按异常暂停的代价：测试集不再是金标集。** 自动标注训练、再用自动标注评估，mAP 衡量的是“和自动标注的一致度”，系统性错误（比如框总是带上底座）能通过所有闸门。
   应对：`model_card.label_source: auto|reviewed`；报告和 webhook 附每个视频 16 帧的缩略拼图，人扫一眼就能发现系统性错误；控制台提供**不阻塞的抽检**，抽检过的帧优先划入 test。
2. **“一个视频 = 一类文物”写进接口契约。** 每个视频必须带类别，VLM 只负责“定位”、不负责“分类”。提示词只放一个类别，准确率更高，也为第 3 点降本打基础。
   （**已修订，见第九节**：真实素材里一段视频常拍了几件不同文物，接口改为每个视频声明它包含的类别列表；“只问声明的类别”的原则不变。）
3. **关键帧 + 插值 + 升级（M2）。** 视频帧高度冗余：每 N 帧调一次 VLM，中间帧用相邻关键帧插值出提示框再给 SAM 收紧，SAM 闸门不过的帧再升级调用 VLM。预计 VLM 调用量降到 35~45%，主要收益是速度和限流余量。M1 先逐帧跑通。
4. **接口必须是异步任务模型。** 训练按小时算，`POST` 只返回 `job_id`，调用方轮询或收 webhook；带幂等键防重复提交；大视频走分片上传。
5. **控制台围绕“定位问题”设计。** 一个 Run 一张详情页：阶段时间线 → 帧数漏斗 → 闸门结果（哪项超阈值、超了多少）→ 一键跳到“只看问题帧”的只读视图 → 训练曲线和日志 → 产物下载。每个失败都给出**错误码 + 人能看懂的原因 + 建议操作**。
6. **单端口：TensorBoard 用 results.csv 曲线替代**（项目里已有 Chart.js），容器内默认不启动 TensorBoard。
7. **类别顺序冻结。** 现在 `update_annotation_project` 改类别顺序不会重映射 `class_id`，会悄悄弄坏标签。流水线项目创建后冻结顺序，一路带到 `labels.txt`。
8. **资源排队对调用方可见。** 训练走全局 GPU 队列，接口返回排队状态；单 Run 帧数上限、VLM 预算上限可配置。
9. **离线可用。** 镜像内预置 `yolo11n.pt`/`yolo11s.pt`/`sam2.1_b.pt`（仓库根目录的 `yolo11n.pt` 已被删除），关闭 Ultralytics 自动安装依赖；Font Awesome 改为本地文件。
10. **负样本缺失。** 单类视频里没有“无文物”画面，端侧容易误报。支持复核确认过的无目标帧和可选的背景图目录进入训练。
11. **历史数据风险。** `tools/scan_bad_rotate_labels.py` 表明旧的旋转增强数据有标签错误，旧数据集不要当金标或校准集。

### v2 文档需要修订的地方
- §3.3/§3.4/§5.5：必经复核 → `review_mode`（auto / on_anomaly / full）；“测试集就是金标集”只在 full 模式下成立。
- §4.2：Run 状态改为 `queued/running/needs_review/succeeded/failed/cancelling/cancelled`；图片状态增加 `auto_accepted`。
- §4.5：重启后**自动续跑**（阶段幂等，attempt+1，最多 3 次），不再标 failed 等人；GPU 锁用 Postgres advisory lock。
- §4.6：工作目录从 `app/static` 移到 `DATA_DIR`。
- §5.8：保留 ONNX(opset12)→onnx2tf 作为唯一路径（与 Android 交接契约一致，避免 Ultralytics 运行时联网装依赖），在 CPU 子进程里执行；关卡 3 中 PT 与 TFLite 的 mAP 必须用同一套 letterbox + NMS 计算，否则下降量没有可比性。
- 新增：对外 API 契约、API Key、webhook、Docker、安全加固（v2 都没覆盖）。

## 三、实施方案

### 0. 关键架构决策
- **一个进程、一个端口**：编排器跑在 uvicorn 进程内（`--workers 1`，关闭 reload）；训练、评估、TFLite 导出全部走子进程。任务通过数据库认领（`FOR UPDATE SKIP LOCKED`），以后拆出独立 worker 容器不用改代码（`PIPELINE_WORKER_ENABLED` 开关）。
- **两套 API 共用一个服务层**：
  - `/api/v1/*`：对外，API Key 鉴权，独立子应用，独立 OpenAPI（`/api/v1/docs`）和错误格式；
  - `/api/pipeline/*`：控制台用（JWT 或 cookie），多了运维动作：放行、覆盖闸门、从指定阶段续跑。
- **测试用 mock VLM**：`VLM_PROVIDER=mock` 返回居中框，CI 和冒烟测试不依赖 OpenRouter。

### A. 对外 API（`/api/v1`）
鉴权：`X-API-Key: myo_sk_<prefix>_<secret>`；权限范围 `pipeline:write/read`、`artifacts:read`；每个 Key 只能看到自己的任务（看别人的返回 404）。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST/PUT/GET | `/uploads`、`/uploads/{id}` | 分片上传（8MiB，`Content-Range`），可续传 |
| POST | `/uploads/{id}/complete` | 校验大小/sha256，用 cv2 探测视频信息 |
| POST | `/pipeline/jobs` | JSON（引用 `upload_id`）或 multipart（`spec` + `videos`）；返回 202 + `Location` |
| GET | `/pipeline/jobs`、`/pipeline/jobs/{id}` | 列表（按 status、external_ref 筛选）/ 详情 |
| GET | `/pipeline/jobs/{id}/events?after=` | 事件时间线（M2 加 SSE） |
| POST | `/pipeline/jobs/{id}/cancel`、`/resume` | 取消；从失败阶段续跑 |
| GET | `/pipeline/jobs/{id}/artifacts[/{name}]` | `delivery.zip`/`model.pt`/`model.tflite`/`labels.txt`/`model_card.json`/`report.json`，带 sha256，支持 Range 请求 |
| GET | `/health`、`/ready` | 存活；就绪（DB、磁盘、GPU） |

请求示例：
```json
{ "name": "batch-2026-10", "external_ref": "crm-123",
  "classes": [{"name":"JadeCup","display_name":"玉杯","prompt":"玉杯（古代玉质饮器）"}],
  "videos": [{"key":"v1","upload_id":"…","class":"JadeCup","expected_instances":1}],
  "review_mode": "on_anomaly",
  "callback_url": "https://…",
  "config": {"extract":{}, "clean":{}, "annotate":{}, "gates":{}, "dataset":{}, "train":{}, "export":{}} }
```
- 校验：`name` 只能是 `[A-Za-z0-9_-]`（会写进 `labels.txt`）；每个类别至少一个视频；epochs ≤ 300；imgsz 是 32 的倍数；视频大小/时长上限；磁盘空间不足返回 507。
- 幂等：`Idempotency-Key` 按 `(api_key, key)` 唯一并存请求哈希。同一个 key、同样内容返回原任务；同一个 key、不同内容返回 409。
- 错误格式：统一为 `{"error":{"code","message","details","request_id"}}`。任务级错误码包括 `no_usable_frames`、`vlm_unavailable`、`gate_failed_hard`、`rejected_by_operator`、`train_failed`、`tflite_verify_failed`、`interrupted` 等。
- Webhook：存进 `webhook_deliveries` 表由编排器投递，至少送达一次；签名 `X-Myolo-Signature: t=..,v1=HMAC_SHA256(secret, "t.body")`；按 10s→3h 退避重试；只拦截私网地址时用 `WEBHOOK_ALLOWED_HOSTS` 放行（本地化部署时需要）。

### B. 编排器与数据模型
新表（`app/models/pipeline.py`、`app/models/api_key.py`）：`pipeline_runs`（状态、阶段状态、冻结的类别和配置、产物相对路径、指标、闸门结果、llm_usage、幂等键、心跳）、`pipeline_videos`（每个视频的类别、元数据、阶段状态和统计，支持单视频重跑）、`pipeline_events`、`pipeline_uploads`、`webhook_deliveries`、`api_keys`（保存 HMAC 哈希、scopes、加密后的 webhook 密钥）。

已有表加字段：在 `init_db.py` 里写一个声明式 `ensure_columns()`，替代现在复制粘贴的 ALTER。
- `ImageAnnotation`：`auto_annotations`、`review_status`（索引）、`risk_score`、`risk_reasons`、`reviewed_by/at`、`pipeline_meta`（视频、帧号、时间戳、清洗指标、所属划分）
- `AnnotationProject`：`review_required`、`pipeline_run_id`
- `Model`：`artifacts`
- `TrainingTask`：`interrupted` 状态、`process_started_at`（防 PID 复用）

阶段（全部幂等）：`ingest → extract → clean → class_check → annotate → gate → [review] → dataset → train → evaluate → export_verify → package`

运行机制：
- 调度线程每 2 秒轮询一次。启动时先做恢复：重新排队孤儿 Run，清理孤儿训练进程（按 PID + 进程创建时间），把旧的 TrainingTask 标为 `interrupted`。
- 每个 Run 在自己的线程里执行，每个工作单元用短生命周期的 `SessionLocal()`，GPU 或网络调用期间不持有 Session。
- GPU 锁 = `pg_advisory_lock`；训练用 `start_new_session=True`，取消时杀整个进程组；成功的判定 = 返回码 0 + `best.pt` + `results.csv`；有 `last.pt` 就 `resume=True` 续训。
- 帧必须放在**一个平铺目录**里，用唯一文件名（`<video>_<frame>.jpg`）：`get_image_file` 是用 `image_directory/name` 拼路径的，子目录会 404。流水线直接批量插入 `ImageAnnotation`，不走 `scan_images`。

DATA_DIR（`/data`）：
```
uploads/  runs/<run_id>/{input/videos, frames/<key>, images/(平铺), manifest.jsonl, vlm_cache/,
                         dataset/{train,val,test}, train/exp, export, delivery/}
static/(旧数据目录)  weights/  config/(SAM 配置)  ultralytics/(YOLO_CONFIG_DIR)
```

### C. 按异常暂停
闸门（默认阈值，可以按 Run 覆盖；结果写入 `gate_results`）：

| 闸门 | 范围 | 警告 | 暂停 |
|---|---|---|---|
| class_check（抽 5 帧、用全部类别提问时与声明类别的一致率；只有 1 类时跳过） | 视频 | <0.8 | <0.6 |
| zero_box_rate | 视频 | >0.10 | >0.25 |
| multi_box_rate（对比 expected_instances） | 视频 | >0.05 | >0.15 |
| vlm_fail_rate | 视频 | >0.02 | >0.05 |
| sam_fallback_rate | 视频 | >0.15 | >0.35 |
| temporal_jump_rate | 视频 | >0.05 | >0.15 |
| tiny_or_truncated_rate | 视频 | >0.2 | >0.4 |
| kept_ratio_after_clean | 视频 | <0.5 | <0.2 |
| usable_frames_per_class | 类别 | <100 | <40 |
| videos_per_class（<3 时退化为按时间段划分，评估会泄漏） | 类别 | <3 | — |
| VLM 预算 | Run | 80% | 100% |

- 帧级风险分沿用 v2 的权重。没有暂停的 Run 会把风险 > 0.6 的帧和 VLM 失败的帧剔出训练，并在漏斗里展示，等于不用人也有一道质量过滤。
- 三种模式：`auto` 只记录、不暂停；`on_anomaly`（默认）任一闸门到“暂停”档就暂停；`full` 必暂停、全部帧进入 `to_review`。
- 暂停后：发 webhook `job.needs_review`；高风险帧标 `to_review`，其余标 `auto_accepted`。
- 控制台操作：逐帧通过/修改/丢弃（复用现有租约和乐观锁）；按视频排除、改类别（只对该视频重跑定位）、重标；`approve`（可覆盖闸门并填写理由，记入事件）/ `reject`。
- 防绕过：`review_required` 项目的 `mark-all-completed` 返回 403；流水线项目在 `annotation.js` 里切换图片时不再自动标完成，改为显式的 A（通过）/ D（丢弃）。

### D. 标注链路
- **M1**：逐帧调用 VLM，提示词只放该视频的类别（沿用 v2 的强约束写法，0~1000 坐标）；多个框时保留最大的并记 `multi_box`。坐标约定做成按模型配置（`coord_mode`），用 20 张图做校准自检。之后 SAM 收框 + v2 质量闸门 → 时序中位数只用于标记离群帧，不替换框。
- `vlm_client`：httpx 异步 + 信号量 + 429/5xx 退避 + 按 `sha1(图片)+模型+提示词版本` 缓存（续跑不重复计费）+ 容错 JSON 解析；图片压缩到长边 1024；OpenRouter 设置 `data_collection: "deny"`。（**已修订，见第九节**：改为放大/缩放到长边 1280，并随请求附每类参考图。）
- 把 `get_shared_sam_model`（`endpoints/sam3.py:92-128`）移到 `services/sam_service.py`；默认 `sam2.1_b.pt`（SAM3 权重需要申请）。
- **M2**：关键帧 + 插值 + 升级（第二节第 3 点）；SAM2 视频传播做技术预研，只有平均 IoU 不低于逐帧方案时才采用。
- **M3**：SAM3 文本提示免 VLM；用历史 Run 训出的模型给同类新视频预标。

### F. Docker 与路径
- **Dockerfile**（合并为一个，删除 `Dockerfile.gpu`）：
  - `python:3.12-slim-bookworm` + torch cu124 wheel（自带 CUDA 用户态库，宿主机只需要驱动 ≥535 和 nvidia-container-toolkit）；
  - apt 装 `ffmpeg libgl1 libglib2.0-0 procps curl tini`；
  - 用 constraints 文件固定 torch/TF/onnx2tf/ultralytics 版本，补上 `httpx` 和 onnx2tf 的依赖；
  - 预置权重到 `/opt/weights`；设置 `YOLO_AUTOINSTALL=false`；非 root 用户运行；
  - 构建时做一次冒烟测试（导入全部依赖 + 导出 yolo11n 到 TFLite）；
  - `HEALTHCHECK`；`CMD uvicorn ... --workers 1 --proxy-headers`。
- **`docker/entrypoint.sh`**：等待 DB → init_db → 创建 DATA_DIR 目录 → 把 `app/static/{datasets,models,extracted_frames,...}` 软链到 `/data/static/*`。这样代码里 38 处写死的 `app/static` 不用改，但 `StaticFiles` 需要加 `follow_symlink=True`。
- **compose**（合并成一个）：
  - `db: postgres:16-alpine`，不映射端口，密码必填；
  - `app` 只映射 `${APP_PORT:-8000}:8000`，配置 `volumes: appdata:/data`、`shm_size: 8gb`、`stop_grace_period: 60s`、GPU reservation；
  - 提供 `.env.example`。
- **端口冲突自动顺延**：
  - 冲突只会出现在**宿主机端口**上（容器有自己的网络命名空间，容器内固定用 8000），所以顺延逻辑放在启动脚本里，不放在镜像里。不用 compose 的端口范围写法（`"8000-8019:8000"`）：Docker 只知道自己分配过的端口，被非 Docker 进程占用时仍可能直接报错，而且用户不知道最后落在哪个端口。
  - 新建 `scripts/start.sh`（Linux 部署机）和 `scripts/start.ps1`（Windows + Docker Desktop），两者逻辑一致：
    1. 起始端口 = 上次成功使用的端口（记录在 `.app_port`），没有则取 `APP_PORT`（默认 8000）；
    2. 预检：端口已被监听（Linux 用 `ss -ltn`，Windows 用 `Get-NetTCPConnection`）就 +1，最多尝试 `APP_PORT_MAX_TRIES`（默认 20）次；
    3. 执行 `APP_PORT=$p docker compose up -d`；如果仍然报 `port is already allocated` / `address already in use`（预检和启动之间被抢占），就 +1 重试；
    4. 成功后把端口写回 `.app_port`（下次优先复用，保证调用方地址尽量不变），并打印 `控制台: http://<host>:<port>/`、`API 文档: http://<host>:<port>/api/v1/docs`；端口与上次不同时给出醒目警告；
    5. `APP_PORT_STRICT=true` 时不顺延，冲突直接报错退出（适合已在防火墙或网关上固定端口的环境）。
  - 本地非 Docker 启动（`run.py` / `start.py`）同样处理：启动前用 socket 尝试绑定 `SERVER_PORT`，被占用就 +1，最终端口打印在启动日志里。
  - 地址不写死端口：接口返回的 `Location`/`links` 一律用相对路径，或基于请求的 base URL（配合 `--proxy-headers`）生成；webhook 里没有请求上下文，配置了 `PUBLIC_BASE_URL` 时才给绝对地址，否则给相对路径加 `job_id`。
- **`.dockerignore`**：补上 app/static 下的各个数据目录、`models/`、`*.exe`、`datasets_import/`、`logs/`、`sam3_config.json`。
- **路径**：新建 `app/core/paths.py`，提供 `to_stored()`（存成相对 DATA_DIR 的路径）和 `resolve_stored()`（旧的绝对路径按 `LEGACY_PATH_PREFIXES` 重映射）。只在 `Dataset.path`、`Model.path`、`image_directory`、`TrainingTask.output_dir` 这几个读取点应用；另提供 `tools/migrate_paths.py --dry-run` 迁移旧数据。

### G. 安全加固（M0 阻断项）
- 所有控制台路由统一加 `Depends(require_console_user)`：接受 Bearer JWT 或 `access_token` cookie（现有很多 JS 用的是不带 header 的 fetch，必须兼容 cookie）。用户、设置、工具、API Key 这几类接口仅限管理员；cookie 鉴权的写请求校验 Origin。

## 六、主要产品风险
1. 不复核就没有真值（第二节第 1 点）。

6. 单进程下的 GPU 和 CPU 争用（advisory lock + 子进程；M2 可拆出 worker）。

### 实测中发现并修正的设计问题
1. **近重复去重误删**：只比较整帧 pHash 时，转台拍摄（背景静止、文物在转）会把不同角度的画面当成重复删掉（合成数据上删了约 40%）。改为 pHash 相近 **且** 缩略图逐像素几乎相同才算重复。
2. **时序检查误报**：清洗删帧后相邻保留帧可能隔了一两秒，直接比较会把正常运动判为“跳变”。改为只与时间窗口内的邻居比较、用前后帧插值预测，且只要有一组邻居能解释就不算离群（一个离群帧不会连累旁边的帧）。
3. **每类 3 个视频时训练数据只剩三分之一**：纯按视频划分只能 1/1/1。新增 `by_video_test`：测试集仍按整段视频留出（指标可信），训练/验证在其余视频内按时间段划分。
4. **短视频按时间段划分时验证集为空**：段长比缓冲带还短，验证段的帧被全部丢弃，训练直接报错。段数改为随时长自适应，缓冲带不超过段长 1/4，并兜底保证验证集非空。
5. **模型没学会也能“成功”**：TFLite 三道校验只证明转换无损，训练不充分的模型 PT 和 TFLite 一样差也能全部通过。新增 `train.min_test_map50`（默认 0.5）质量警告，写入事件与模型卡，可配置为直接失败。
6. **两种 mAP 口径混在一起**：Ultralytics 评估（多标签 NMS）与端侧口径（单标签 NMS）在训练不充分时差距很大，模型卡中分开列出并注明。

## 九、真实文物视频上的自动标注调优（2026-10-09）

用平台里已人工标注的真实文物数据（25 段视频、6 类、1539 帧：办公桌面杂物多、文物普遍很小，多数视频同时拍了几件文物）
做校准，工具 `tools/calibrate_vlm.py`（召回 = 人工框被 IoU≥0.5 且类别正确地找到的比例）。

### 校准结论（qwen3-vl-235b，100 帧 / 153 个人工框，只问该视频声明的类别）

| 设置 | 召回 | 精确 | 每帧费用 |
|---|---|---|---|
| 文字描述（原默认：30b、strict 提示词） | 0.17 | 0.68 | — |
| 文字描述（recall 提示词、235b） | 0.34 | 0.73 | $0.00016 |
| 放大到 1280 | 0.41 | 0.89 | $0.00034 |
| 参考图 | 0.42 | 0.52 | $0.00022 |
| **放大 + 自动挑选的参考图（新默认）** | **0.72** | **0.84** | $0.00042 + 每任务约 $0.03~0.05 |
| 放大 + 人工框裁出的参考图（上限） | 0.74 | 0.85 | $0.00041 |

- 放大与参考图单独用都几乎没用，合在一起召回翻倍：小图上模型对照参考图反而乱框，放大后才找得到。
- 只问声明的类别比问全部类别精确率高约 15 个百分点（0.83 vs 0.68），保留“只问声明类别”的原则。
- SAM 收框在 235b + 放大后几乎不再提升 IoU（0.757 → 0.756），默认仍开启（有闸门保护，不会变差）。
- 30b 同样设置召回约 0.53，8b、qwen3.6-flash 明显更差；默认模型改为 `qwen/qwen3-vl-235b-a22b-instruct`。

### 设计调整
1. **视频可声明多个类别**：`videos[].classes`（与 `class` 二选一）。标注时只问该视频声明的类别；件数上限 `expected_instances`
   按类别计；时序检查按类别分轨；闸门的每类可用帧数按框计；按视频划分改为多标签贪心分配（每类都有测试视频、每类训练集至少留 1 个视频）。
2. **参考图阶段 `references`**（在类别校验之前）：调用方提供的优先；没提供的类别自动挑选——只放大、不带参考图检测
   该类别的探测帧（这种设置精确率最高，候选与人工框比对约 40 个里只错 1 个），分轮探测直到碰到足够大的候选，
   再把候选周围区域单独给模型核对：认出是该类 → 采用；认成别的类 → 丢弃；什么都没认出 → 单类视频里的候选兜底采用，
   只出现在多类视频里的类别先带上其他类别已确认的参考图再核对一次，仍不确定时取外观最一致的候选并警告请人确认。
   控制台“类别”卡片展示每类用的参考图。
3. **类别校验带参考图提问、只统计认出了东西的帧**：只给文字时模型把绣品认成“书画”，把声明正确的视频误报为选错类别；
   把“什么都没认出”的帧算进分母，会让召回一般的模型频繁误报。认出物品的帧少于 3 帧时不判定；抽查帧数默认 8，所有视频一起并发。
4. **默认并发 8**：235b + 1280 + 参考图单次请求约 10~15 秒，并发 4 时每分钟只能标约 20 帧。
5. **探测帧在该类别的所有视频间轮流取**（单类视频排在每轮前面），每类最多 48 帧、够用即停：唯一的单类视频里文物特别小时，
   先取完单类视频会把探测全花在它身上、一个候选都找不到。
6. **时序检查按图像大小给偏移容差下限**（图像对角线 2%），并用面积比代替 IoU：小物件的框手持一晃就超出“框对角线 × 0.2”。
   在真实视频上被判离群的帧从 35 降到 24，抓到的错框数不变。
7. **`tiny_or_truncated_rate` 改为只警告**：文物本来就小的素材很常见，实测按它暂停的视频标注都是对的。
8. **数据集新增 `hybrid` 划分**：只有部分类别视频不足 3 个时，只把含这些类别的视频按时间段划分，其余仍整段留出测试集；
   以前一个类别视频少，所有类别都退化成按时间段划分。
9. 修复对外接口：multipart 建任务时不能混用 `upload_id`（示例客户端“大文件分片、小文件随请求上传”的用法会 422）。

用上面数据集里 14 段视频（6 类，其中 7 段是多类视频，按帧重新合成视频）经控制台接口提交，`on_anomaly` 模式、真实 235b 视觉模型：

| | 第 1 轮（调优前的阶段顺序与挑图逻辑） | 第 2 轮（参考图前置、二次核对、外观一致兜底、闸门调整） |
|---|---|---|
| 自动标注 vs 人工框（全部 689 帧） | 召回 0.70 / 精确 0.92 / IoU 0.79 | 召回 0.74 / 精确 0.93 / IoU 0.79 |
| 进训练集的帧 | 召回 0.83 / 精确 0.93 | 召回 0.80 / 精确 0.94 |
| 古碗（只出现在多类视频里） | 无参考图，召回 0.14 | 外观一致兜底挑到参考图，召回 0.86 |
| 玉杯 | 有参考图，召回 0.37 | 探测帧全落在小物件视频、没挑到参考图，召回 0.15（已修，见第 5 条） |
| 暂停的视频 | 7 个（多数是误报：小物件、类别校验把绣品认成书画） | 3 个（2 个确有问题） |
| 视觉模型费用 | $0.34（895 次调用） | $0.34 |

第 1 轮放行后跑完训练（yolo11n、40 轮）、测试集评估、TFLite 三道校验（数值误差 0.005 像素、mAP 无下降）与打包，任务成功。
交付的模型在同一批测试帧上**改用人工框评估**：mAP50 0.913（自动标注口径 0.784）、mAP50-95 0.560（自动标注口径 0.726）；
玉杯 0.864 / 古碗 0.662，其余四类 ≥ 0.968。即：用自动标注当测试集时 mAP50 偏低（自动标注漏标的物品被模型找到反而算误报），

测试帧与训练帧同源，以上数字偏乐观（第 8 条 hybrid 划分即为此而加）。

第 3 轮（全部改动 + 并发 8）：自动挑选给 6 类中的 5 类挑到了参考图（古碗这次直接核对通过），玉杯 48 帧探测只出现 1 个候选、
核对时被认成古碗而丢弃——玉杯是最难的一类（多数帧里只占画面 0.2~0.5%，外观又与碗相近），自动挑选给不了保证。
标注后召回 0.73 / 精确 0.94，只有 2 个视频暂停且都确有问题。随后在控制台**把一帧里框准的玉杯“设为参考图”**
（只重标含玉杯的 6 个视频、约 330 帧，$0.16）：玉杯召回 0.13 → 0.49，纯玉杯视频 s2_5 召回 0.07 → 0.87，

mAP50-95 0.525（自动标注口径 0.824，差距来自框的松紧习惯）。全程没有人工逐帧标注，只做了一次“设为参考图”。

### 尚未解决 / 下一步
- 玉杯这类极小件（占画面 < 0.5%）自动挑参考图不稳定，建议调用方为小件文物提供参考图；控制台缺图时已警告并给出“设为参考图”入口。
- OpenRouter 同一模型会路由到不同后端，temperature=0 也不完全可复现（同一批帧两次运行的检出数不同）；可考虑在请求里固定 provider。
- 小件文物的时序检查仍偏敏感（s2_5 杯子约 23 像素，框跳变比例 0.5，实际精确率 0.87）。
- 每类视频很少时，整段留出测试视频会占掉约 40% 的数据（本例 255/634 帧），训练数据偏少；建议每类 ≥ 4~5 个视频。
- 关键帧 + 插值（M2）仍是降低费用和耗时的主要手段：当前约 $0.0005/帧、并发 8 时约 80 帧/分钟。
